## Diagnosis

This is different from every other fix on this page: **the moment a secret is pushed, treat it as compromised.** Anyone who cloned, forked, or has cached views of the repository may already have it, and GitHub's own secret scanning may have indexed it. Deleting it from history later does not undo that exposure.

## Fix

**Step 1 — rotate the credential first, always.** Revoke the API key, reset the password, or regenerate the token at its source. This is the step that actually protects you; everything below is cleanup.

**Step 2 — remove it from history.** The modern, recommended tool is `git-filter-repo` (the old `git filter-branch` is slow and easy to misuse):

```bash
pip install git-filter-repo
git filter-repo --path path/to/secret-file --invert-paths
```

That rewrites history to act as if the file never existed. To scrub a secret string that's scattered across many files instead of one whole file, use a replacement rule:

```bash
echo 'MY_SECRET_VALUE==>REMOVED' > replacements.txt
git filter-repo --replace-text replacements.txt
```

**Step 3 — force-push the rewritten history**, and have every collaborator re-clone rather than pull (rewritten history conflicts with their old copies):

```bash
git push origin --force --all
git push origin --force --tags
```

**Step 4 — add the file to `.gitignore`** going forward so it can't happen again, and consider a pre-commit secret scanner.

<Callout type="warning">
Rewriting history changes every commit hash after the affected commit. Coordinate with your team before force-pushing a shared branch — this is one of the few times a hard force-push to a shared branch is the correct move, but everyone needs to know it's coming.
</Callout>
