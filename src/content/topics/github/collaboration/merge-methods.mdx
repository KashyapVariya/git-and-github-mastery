## Why it matters

When a pull request is approved and its checks pass, clicking the merge button isn't a single choice — GitHub offers three different *methods*, and they leave genuinely different traces in your project's history. Picking the wrong one for your team's habits doesn't break anything today, but it can make `git log` and `git blame` noticeably harder or easier to read months from now.

## Merge commit

The default. GitHub takes every commit from the pull request's branch as-is and joins them into `main` with a new **merge commit** on top, exactly like running `git merge --no-ff` locally.

```text
* 9f3a1c2 Merge pull request #42 from add-search-filter
|\
| * 7b2e001 fix typo in filter label
| * 4d19aa3 add search filter component
|/
* 1a0c9de previous commit on main
```

You keep every individual commit, plus a clear marker of when and how the branch came in. The trade-off: if a contributor made ten small "wip" commits, all ten land permanently in `main`'s history.

## Squash and merge

Combines every commit on the branch into a **single new commit** on `main`, using the pull request's title and description as the commit message by default.

```text
* e77c410 Add search filter (#42)
* 1a0c9de previous commit on main
```

This keeps `main`'s history clean — one commit per feature, regardless of how messy the branch's own history was. It's the most popular default for teams that don't care about preserving a contributor's exact commit-by-commit process. The trade-off: you lose the individual commits' granularity, which occasionally matters for `git bisect` or fine-grained blame.

## Rebase and merge

Takes each commit from the branch and replays it individually onto the tip of `main`, with no merge commit at all — the branch's commits just become the newest commits on `main`, back to back.

```text
* 7b2e001 fix typo in filter label
* 4d19aa3 add search filter component
* 1a0c9de previous commit on main
```

This gives a fully linear history — no merge commits anywhere — while still preserving each individual commit. The trade-off: it rewrites the commit hashes from the original branch, so anyone with a local copy of that branch will see it diverge from what's now on `main`.

## Choosing one

| Method | History shape | Keeps individual commits | Rewrites hashes |
|---|---|---|---|
| Merge commit | Branching, with merge markers | Yes | No |
| Squash and merge | Linear, one commit per PR | No | N/A |
| Rebase and merge | Fully linear | Yes | Yes |

A repository's settings (**Settings → General → Pull Requests**) can restrict which methods are even available, so a whole team stays consistent instead of each merge looking different.

<Callout type="golden">
There's no universally "correct" method — squash-and-merge is the safest default for most teams because it keeps `main` readable regardless of how any individual contributor commits. Reach for merge commits or rebase only once you have a specific reason to want that shape of history.
</Callout>

## Try it yourself

Open a repository's Pull Requests settings and see which merge methods are enabled. Then browse its `main` branch history — can you tell, just from the shape of the log, which method the team actually uses?
