## Why it matters

Committing an API key or password is one of the easiest mistakes to make and one of the most damaging — the moment it's pushed, treat it as compromised (see [I committed a secret or credential](/fix-it/remove-secret-from-history) for what to do if it already happened). Secret scanning exists to catch this before, and immediately after, it happens.

## Two layers of protection

**Secret scanning (detection)** continuously checks your repository's content — including full history — against known credential patterns from over a hundred service providers (AWS, Stripe, Slack, and more). When it finds a match, it opens an alert and, for many providers, automatically notifies the provider so they can revoke the leaked credential on their end.

**Push protection** is the stronger, preventative layer: it checks commits *at push time* and blocks the push outright if it detects a secret, before it ever lands on GitHub. The person pushing sees exactly what was found and where, and has to either remove it or explicitly (and visibly) bypass the block.

## Turning it on

For public repositories, secret scanning is on by default. For private repositories, an organization or repository owner enables it under Settings → Code security. Push protection is a separate toggle in the same settings panel, and can be enabled organization-wide so no individual repository can opt out silently.

<Callout type="golden">
Push protection is far more valuable than detection alone — a secret that's blocked before it's pushed never has to be rotated or scrubbed from history. Turn it on everywhere you can.
</Callout>

<Callout type="warning">
Secret scanning detects *known patterns*. A custom internal token format won't be recognized automatically — for those, you can define custom patterns in an enterprise or organization's settings.
</Callout>

## Try it yourself

Check whether secret scanning and push protection are enabled on a repository you maintain (Settings → Code security). If you manage an organization, check whether you can enforce push protection at the organization level instead of relying on every repository owner to turn it on individually.
