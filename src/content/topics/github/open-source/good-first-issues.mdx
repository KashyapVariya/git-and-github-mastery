## Why it matters

Picking your first open-source contribution can feel paralyzing — the codebase is unfamiliar and every issue looks intimidating. Maintainers know this, so many label a subset of issues specifically for newcomers.

## What to look for

- **The `good first issue` label** — a near-universal convention. It signals the maintainer believes this task is small, well-scoped, and doesn't require deep project knowledge.
- **The `help wanted` label** — broader than good-first-issue; it just means the maintainer would welcome outside help, not necessarily that it's beginner-friendly.
- **GitHub's own search** at [github.com/topics/good-first-issue](https://github.com/topics) lets you filter across every public repository by this label and by programming language.

## Reading an issue before you commit

A good issue to start with usually has:

- A clear description of the current (wrong) behavior and the expected (right) one
- No unresolved debate in the comments about *whether* to fix it — just *how*
- No one already assigned or actively working on it

<Callout type="tip">
Comment on the issue before you start — something as simple as "I'd like to try this one." It prevents two people from duplicating the same work, and gives the maintainer a chance to warn you about anything tricky.
</Callout>

## If you get stuck

Ask, in the issue thread, specifically. "I tried X and got Y — is that expected?" gets a far more useful answer than silence, and most maintainers are glad to help someone who's clearly already made an effort.

<Callout type="golden">
Your first contribution doesn't have to be code. Fixing unclear documentation, adding a missing example, or improving an error message all count — and they're often labeled good-first-issue too.
</Callout>

## Try it yourself

Search GitHub for `label:"good first issue" language:javascript` (swap in a language you know) and read through five results. Notice which ones feel approachable to you and why — that instinct gets sharper with practice.
